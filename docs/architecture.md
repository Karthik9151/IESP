# IESP Architecture

## 1. High-level architecture

```text
Email provider
   ↓
Mail-provider abstraction
   ↓
Email ingestion
   ↓
Safe MIME/header parsing
   ├──────────────→ Security feature analysis
   ↓
NLP preprocessing
   ↓
TF-IDF + SVM phishing baseline
   └──────────────→ Security Decision Engine
                         ↓
        PHISHING / SUSPICIOUS / NON-PHISHING / REVIEW REQUIRED
                         ↓
             eligible non-phishing only
                         ↓
             VADER + engineered features
                         ↓
                Logistic Regression
                         ↓
                    P1 / P2 / P3
                         ↓
                      FastAPI
                         ↓
                 React/Vite dashboard
                         ↓
                    Persistence
```

The enhanced security engine surrounds the academic ML baselines. Security classification is authoritative and always precedes priority classification.

```text
│   └── integrations/
│       └── mail/         # Gmail/Graph/IMAP adapters

├── models/

├── infra/
├── docs/

```

This is a target structure. Milestone 0 does not create unnecessary empty implementation files.

## 3. Data flow

1. Provider adapter retrieves permitted mail data.
2. Ingestion normalizes provider-specific messages.
3. MIME/header parser extracts structured information without executing content.
4. Untrusted content is treated as data.
5. NLP features and security features are produced.
6. Academic phishing evidence is generated by TF-IDF + SVM.
7. Security Decision Engine evaluates ML evidence plus deterministic security signals.
8. The engine emits PHISHING, SUSPICIOUS, NON-PHISHING, or REVIEW REQUIRED.
9. Only eligible non-phishing messages enter the priority classifier.
10. Priority model emits P1/P2/P3.
11. FastAPI exposes the normalized result.
12. React displays the result safely.
13. Persistence stores only data justified by the retention policy.

## 4. ML pipeline

### Academic phishing baseline

```text
normalized email text → preprocessing → TF-IDF → SVM → phishing evidence
```

Raw SVM decision scores are not probabilities. If probability semantics are required, calibration must be explicitly implemented and evaluated.

### Academic priority baseline

```text
eligible non-phishing email
        ↓
VADER + approved engineered features
        ↓
Logistic Regression
        ↓
P1 / P2 / P3
```

Priority labels are proxy/project labels unless backed by genuine human annotation. They must not be presented as objective human urgency.

## 5. Security pipeline

Security analysis should include, as applicable:
- MIME/content-type validation.
- Header consistency.
- Authentication-related provider signals.
- Sender/domain indicators.
- URL structural indicators.
- Attachment metadata/policy checks.
- ML phishing evidence.
- Deterministic escalation/review rules.

The engine must support REVIEW REQUIRED for ambiguous or conflicting evidence.

### Required security principles

- Email content is untrusted input.
- Never execute attachments.
- Never automatically visit extracted URLs.
- Protect all URL/network handling against SSRF.
- Never expose API keys.
- Never store passwords.
- Do not log full email bodies by default.
- Email content must never control application behavior or become executable instructions.
- Do not treat SVM decision scores as probabilities unless calibrated.
- Do not claim proxy priority labels represent human judgment.
- Security classification must happen before priority classification.

## 6. API layer

FastAPI is the application boundary.

Responsibilities:
- Request/response validation.
- Versioned API contracts.
- Analysis service orchestration.
- Health/readiness.
- Safe error handling.
- Authentication/authorization when required.
- Secret and sensitive-content isolation.

Conceptual endpoint:

`POST /api/v1/analyze`

The exact schema is deferred until the domain model and analysis engine are implemented.

## 7. Frontend

React/Vite provides:
- inbox/results view;
- security classification and reasons;
- review-required queue;
- priority P1/P2/P3 only when applicable;
- message detail using safe/sanitized rendering;
- API error/loading states.

Raw email HTML must never be trusted directly by the browser.

## 8. Database

A relational database such as PostgreSQL is the intended production persistence layer.

Potential stored entities:
- normalized message metadata;
- analysis results;
- security signals/reasons;
- review state;
- provider linkage;
- minimal audit metadata.

Passwords must never be stored. Provider credentials/tokens must use an appropriate secret/token mechanism, not ordinary application tables. Retention and minimization rules must be defined before production.

## 9. Mail-provider abstraction

The analysis engine must not depend directly on provider-specific objects.

Conceptual interface:

```text
MailProvider
├── authenticate()
├── list_messages()
├── fetch_message()
└── normalize_message()
```

Adapters:
- Gmail API
- Microsoft Graph
- IMAP

Use least-privilege permissions, OAuth where supported, and explicit timeout/retry/error handling. Provider-specific failures must never bypass security classification.

## 10. Deployment architecture

Planned shape:

```text
Users
  ↓ TLS
Reverse proxy / ingress
  ├── React frontend
  └── FastAPI backend
          ├── analysis engine + model artifacts
          ├── PostgreSQL
          └── mail providers
```

Docker and CI/CD are Milestone 8. Production deployment is Milestone 10.

Production requirements include TLS, external secret management, restricted networking, database access controls, vulnerability scanning, secret scanning, safe logging, health monitoring, backups, and rollback procedures.

## Dataset issue

The specification contains conflicting dataset information:
- 900 emails in one section.
- 5,572 rows reduced to 5,169 unique records elsewhere.

Milestone 0 deliberately does not choose either count. Milestone 1 must verify the actual source, row count, duplicate count, unique count, labels, provenance and licensing/usage constraints.

## Deferred decisions

Exact dataset source, model hyperparameters, security thresholds, database schema, provider scopes, authentication mechanism, retention period, hosting platform and scaling configuration are intentionally deferred to their relevant milestones.

No performance or security-effectiveness results are claimed by this architecture.
